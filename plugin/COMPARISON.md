# Team Chat 0.2.0 제품 비교와 10회 개선

2026년 11월 12일 기준 공개 문서와 DeepSeek Harness 0.2.2-rc.1 소스를 사용했다. Muse는 Meta의 개인 에이전트를 뜻한다. 각 제품의 모델 속도와 상용 서비스 지연은 동일 조건에서 측정하지 않았다.

| 기준 | Grok Bot | Meta Muse | Hermes Bot Mode | Team Chat 0.2.0 |
| --- | --- | --- | --- | --- |
| 기능과 실행 단위 | Bot 2~6명과 그룹 채팅, 멘션, 메시지 답장, Bot 간 직접 인계 | 한 개인 에이전트가 작업·목표를 관리하고 일정과 이벤트에 반응. 내부 하위 에이전트 사용 | 기존 Hermes 프로필을 Bot으로 표시. 개인 대화, 그룹 대화, Bot 간 인계와 루틴 | 기존 DSH 리드·팀원 세션 ID에 방 하나 연결. 멘션, 답장, 제한된 후속 라운드, 사용자 답변 우선 처리 |
| 실행 제어 | 직접 사용자 요청에 따른 액션 승인. 그룹에서는 요청한 사용자가 해당 결정을 내림 | 전용 Secure VM, Sentinel을 통한 외부 동작 통제, 사용자 승인 | 방의 후속 발언 대기열과 중지·재개, 팀원별 보류, 질문과 최근 상태 | 현재 요청 중지와 대기열 취소를 분리. 최신 실행 ID를 대조. 한 팀원에 대한 명시적 도구 허용과 원본 DSH 승인 |
| UI | 메신저형 사이드바와 타임라인에 파일·질문·도구 활동 표시 | 대화와 백그라운드 작업 진행을 함께 표시. 중요한 결정에는 구조화된 UI 사용 | 프로필 목록, 상태·최근 메시지, 멤버 관리, 질문 대기 표시 | 멘션 키보드 완성, 방별 초안, 현재 상태와 대기열 미리보기, 불러온 기록 검색, 원본 세션으로 이동 |
| 성능을 좌우하는 구조 | 모델·클라우드·클라이언트를 포함하는 서비스. 공개 문서에서 동일 워크로드 수치를 확인할 수 없었음 | 백그라운드 작업과 하위 에이전트 동시 실행 구조. 사용자의 작업과 VM 비용에 따라 달라짐 | 그룹 멤버 발언과 후속 대기열을 제어. 모델과 게이트웨이는 사용자 설정에 따름 | 방당 순차 실행 유지. 변경분 전송, 과거 기록 분할, 공유 프롬프트 한도 적용. 아래 수치는 Team Chat 내부 전후 비교 |

## 개선 회차

| 회차 | 관찰 | 반영 및 검증 |
| ---: | --- | --- |
| 1 | 기존 중지는 현재 응답과 대기 요청을 함께 제거했다. 동일 ID를 다른 내용으로 다시 보내도 성공 처리했다. | 중지 범위를 분리하고 실행 ID를 확인한다. 동일 내용만 멱등 처리하는 회귀 테스트를 추가했다. |
| 2 | 도구 체크박스와 `@all`을 함께 사용하면 첫 라운드 전체에 도구가 허용될 수 있었다. | 직접 호출한 한 명에게만 이번 메시지의 도구 권한을 부여한다. 후속 발언과 모호한 호출을 검증했다. |
| 3 | 팀원이 `@user`를 사용해도 이전에 대기 중이던 요청이 진행됐다. | 답변 대기 상태를 저장하고 명시적 답변을 앞에 배치한다. 재개는 현재 질문 ID를 확인한다. |
| 4 | 채팅방에서 응답 지연과 DSH 원본 승인을 구분하기 어려웠다. | 승인·질문 대기와 원본 세션 이동을 제공한다. 플러그인은 DSH 승인 결정을 위임하고 대기 해제를 관찰한다. |
| 5 | 활동 중 350ms마다, 유휴 중 1초마다 전체 페이지를 조회했다. | 최초 스냅샷 이후 변경 위치만 보내는 Typert 스트림과 연결 복구를 구현했다. 느린 소비자의 초기화와 취소를 검증했다. |
| 6 | 현재 메시지가 이력과 별도 요청에 중복됐고, 문자 길이만 제한해 UTF-8 직렬화 크기가 커질 수 있었다. | 공유 이력을 직렬화된 UTF-8 12,000바이트로 제한하고 현재 메시지를 한 번 넣는다. 인용과 코드 펜스 파싱을 보강했다. |
| 7 | 저장 시 오래된 메시지까지 매번 복제하고 직렬화했다. | 확정된 64개 메시지 단위 보관과 절대 위치를 도입했다. 이전 형식 로드, 중간 쓰기 실패, 중복 요청과 페이지 경계를 검증했다. |
| 8 | 문자열 끝에서만 멘션을 완성했고, 다른 방을 열면 초안을 잃을 수 있었다. | 커서 기준 멘션과 키보드 조작, 방별 초안, 동일 요청 재시도의 ID 유지를 구현했다. |
| 9 | 현재 활동, 대기 요청, 중단 메시지의 처리 방법이 화면에서 분산돼 있었다. | 활동과 대기열, 검색, 최신 메시지 이동, 사용자 확인이 필요한 다시 작성 기능을 구현했다. |
| 10 | 합성 단위 테스트로는 실제 DSH 플러그인 로딩, 데이터 이전, 브라우저 스트림을 증명할 수 없었다. | DSH 0.2.2-rc.1과 Chromium을 사용해 실제 설치, 기존 세션 호출, 기록 이전, 중지, 승인 이동, 유휴 네트워크 트래픽을 확인했다. |

## 측정과 실행 검증

| 항목 | 0.1.0 | 0.2.0 | 측정 조건 |
| --- | ---: | ---: | --- |
| 유휴 HTTP 조회 | 15회 | 1회 | DSH 0.2.2-rc.1과 Chromium에서 방을 연 뒤 12초. 목록 4→1회, 방 조회 11→0회. 0.2.0은 대화방 스트림 하나를 연결 |
| 메시지 추가당 직렬화한 데이터 | 1,828,699바이트 | 45,928바이트 | 합성 기록 5,000개에서 256개를 추가. 0.2.0의 방 레코드와 추가 보관 묶음 합계. 97.49% 감소 |
| 복제와 직렬화 중앙값 | 17.959ms | 0.316ms | Node 24.22.1, 같은 합성 벤치마크. 인메모리 테스트이므로 디스크 fsync나 모델 지연을 포함하지 않음 |

단위 테스트 26개를 통과했다. 실제 DSH 호스트에서 0.1.0 방의 254개 레코드와 절대 위치를 비교했다. 보관된 요청 ID에 동일한 내용을 다시 보내면 추가 기록이 생기지 않고, 내용을 바꾸면 오류가 발생했다. 기존 리드·팀원 ID와 모델 실행을 호스트 재시작 뒤 확인했다. Chromium과 테스트 모델을 사용했으며 Windows/macOS Desktop 앱의 직접 설치와 실제 모델 TPS는 검증 범위 밖이다.
